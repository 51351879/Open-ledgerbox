# 威胁模型

> 短、诚实、不吹。在这个品类里，一份说清楚「我们不保护什么」的文档，比任何徽章都更能建立信任。
>
> 最后更新：2026-08-02（P0）

---

## 1. 安全边界

**边界就是「这台机器的当前本地用户」。** 没有别的。

ledgerbox 是单人本地工具：没有账号、没有认证、没有权限系统。任何能以你的身份登录这台机器的人，都能读你的账本——就和他们能读你的报税文件、浏览器密码库一样。

---

## 2. 存了什么

| 位置 | 内容 |
|---|---|
| `archive/` | **对账单 PDF 原件**：含法定姓名、街道地址、完整账号 |
| `ledger.db` | 交易明细、逐笔余额、商户名、**第三方对手方姓名**（Zelle 收付款人）、含城市/州的商户串 |
| `extracted/` | PDF 文本层抽取结果（同上，加坐标） |
| `export/` | beancount 纯文本导出（同上） |

**对手方姓名值得单独说**：Zelle 交易里出现的是**别人**的真实姓名，他们从未同意出现在你的任何文件里。这是「不要把这些文件传到任何地方」的独立理由——即使你本人不在乎自己的隐私。

---

## 3. 静态加密

**没有。**

`ledger.db` 和 `archive/` 下的 PDF 都是明文。唯一的保护是**你的磁盘卷本身**是否加密（Windows BitLocker / macOS FileVault / Linux LUKS）。

我们明说而不是暗示。如果你的笔记本没开全盘加密，丢了就等于把 13 个月的账号、余额、住址一起送人。

---

## 4. 网络

| 项 | 状态 |
|---|---|
| 监听地址 | 只绑 `127.0.0.1`（P1 起）。**不监听 `0.0.0.0`** |
| 出站请求 | **零**。无遥测、无版本检查、无崩溃上报 |
| CDN | **零**。前端所有资源本地 vendor |
| 银行连接 | **无**。不自动取数，见 `docs/AUTOMATION.md` |

不要把这个服务暴露到局域网或公网。它没有认证——那不是疏忽，是「边界是本机用户」的直接后果。

---

## 5. 数据位置与运行时守卫

用户数据默认落在操作系统数据目录，**物理上在仓库之外**：

| 系统 | 路径 |
|---|---|
| Windows | `%LOCALAPPDATA%\ledgerbox\` |
| macOS | `~/Library/Application Support/ledgerbox/` |
| Linux | `~/.local/share/ledgerbox/` |

`.gitignore` 是缓解措施，**物理隔离才是控制措施**。因此还有一条运行时守卫：

> **拒绝把用户数据写进任何位于 git 仓库内的目录**（向上遍历全部祖先，`.git` 是目录或文件都算）。

触发时 ledgerbox 直接退出并给出可操作的提示。

### 5.1 如果守卫拒绝了默认目录

这**不是** bug。常见原因是你的主目录本身是个 git 仓库（`git init ~` 管理 dotfiles，或者手滑建的空仓库）。那样一来 `%LOCALAPPDATA%` 就在仓库里，一次 `git add -A` 就可能把财务数据暂存进去。

两个出路：

```bash
# 一次性指定
ledgerbox --data-dir /some/path/outside/any/repo ingest statement.pdf

# 或者设成默认
export LEDGERBOX_DATA_DIR=/some/path/outside/any/repo    # Windows: setx
```

### 5.2 portable 模式（把数据放在项目旁边）

**不支持，且是有意的。** 如果你想把数据目录放在一个 git 仓库里（比如想版本化你的账本），你需要显式地把它指向一个**不含 `.git` 的目录**，然后自己决定如何备份。

如果你确实想版本化，正确做法是版本化 `export/ledger.beancount` 和 `archive/`——放进一个**专门的私有仓库**，而不是放进 ledgerbox 的源码仓库。见 README「Back it up three ways」。

## 6. 明确不在防护范围内

| 不防 | 说明 |
|---|---|
| 恶意的本地用户 | 与「边界是本机用户」直接冲突 |
| 被入侵的操作系统 | 键盘记录器、rootkit —— 无解 |
| 恶意浏览器扩展 | 扩展对 `127.0.0.1` 页面有完整访问权 |
| 磁盘取证 / 冷启动攻击 | 见 §3 |
| 供应链攻击 | 缓解手段是依赖极少（P0 只有 2 个运行时依赖）+ 全部锁版本，不是零风险 |
| 你自己把 `archive/` 传到云盘 | 工具管不了 |

---

## 7. 摄入路径上的输入安全

对账单 PDF 是**外部输入**，即使它来自你的银行：

- 上传大小上限（默认 50 MB），扩展名 + magic bytes 双重校验（P1）
- PDF 解析在 pdfplumber 内进行，不执行 PDF 里的任何 JavaScript / 嵌入内容
- 商户名与 Zelle 备注是**第三方可控文本**：任何渲染路径必须转义，绝不 `innerHTML` 拼接（P2）
- 单个文件解析失败不影响其他文件，也绝不导致部分写入——对账不过就整张不入账

## 8. 报告安全问题

见 `SECURITY.md`（P5 交付）。

**无论何时：不要把真实对账单、真实交易数据、或任何含账号/姓名/地址的文件附到 issue、PR 或讨论里。**

脱敏工具 `tools/sanitize.py` 与合成数据生成器 `tools/gen_synthetic.py` 都还**没有写**（P5）。在它们到位之前，**不要手工脱敏真实账单**——用 `tests/synth.py` 按坐标构造合成账单，那份代码从来没有过真实数据。理由见 [`ADDING_A_BANK.md`](ADDING_A_BANK.md)。
